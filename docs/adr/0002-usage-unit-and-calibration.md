# ADR-0002 — 사용량 단위·5시간 구간·한도 보정

- 상태: 승인 (2026-10-07, 지휘부)
- 관련: `docs/PLAN.md` §4.1, ADR-0001

## 맥락

- 계정의 한도 %는 서버 값이라 로그에 직접 들어 있지 않다. 다만 **Claude Code가 상태줄 스크립트의 stdin JSON으로 실제 값을 넘겨 준다.** 해당 필드는 `rate_limits.five_hour.used_percentage`·`resets_at`(epoch 초)과 `rate_limits.seven_day.*`다. Pro/Max 구독에서 세션의 첫 응답이 온 뒤부터 들어오고, 창마다 없을 수도 있다(code.claude.com/docs/en/statusline). claude-monitor도 최근 이 값을 "official"로 쓰기 시작했다.
- 로그 안에는 `quotaLimits.resetsAt`가 아주 드물게(5건) 있고, `cost-state.totalCostUSD`가 세션별로 있다.
- 선행 도구들의 5시간 구간은 모두 **첫 활동 시각을 UTC 정시로 내림**하고 5시간 공백이 생기면 새로 시작하는 휴리스틱이다(ccusage, claude-monitor). 그런데 사용자가 관측한 초기화 시각은 15:06으로 정시가 아니다. 정시 내림은 실제 경계와 최대 59분 어긋날 수 있다.
- 가격 처리도 도구마다 다르다. claude-monitor는 가격표가 하드코딩돼 있고 1시간 TTL 캐시 쓰기를 1.25배로 계산한다(과소). ccusage는 실행 중 LiteLLM 가격을 받아 오는데, 이는 네트워크를 쓰므로 우리 원칙 위반이다.
- 실측해 보니 1시간 TTL 캐시 쓰기가 실제로 크다. 10/06 fund-agent 세션에서 한 호출이 `ephemeral_1h_input_tokens` 458,116을 기록했다(보고서 참조).

## 결정

1. **사용량 단위 = API 정가 환산 USD(“단위 $”)**. 토큰 종류별로 따로 매긴다.
   - input = 1×
   - output = 모델 output 가격
   - cache_read = 0.1×
   - cache_write_5m = 1.25×
   - **cache_write_1h = 2×**
   - web_search = 건당 요금
   - 가격표는 패키지에 동봉한 `pricing.toml`(모델·적용 시작일·출처 URL)로 둔다. 실행 중에는 받아 오지 않는다.
   - 모르는 모델은 같은 계열의 가격으로 대체하고 `price_estimated=1`로 표시한다.
   - 가격 값은 M1에서 공식 가격 문서로 채우고 출처와 확인일을 적는다.
2. **5시간 구간 경계는 다음 우선순위로 정한다.**
   - ① 상태줄로 기록한 `five_hour.resets_at`
   - ② 로그의 `quotaLimits.resetsAt`
   - ③ 사용자가 보정 입력한 초기화 시각
   - ④ 앞의 셋이 다 없을 때만 ccusage식 휴리스틱(정시 내림 + 5시간 공백). 이 경우 "추정 경계"로 표시한다.
3. **한도 % 보정**: 표본 하나 = (구간 시작, 구간 끝, 관측한 % 변화, 출처)다.
   - 출처는 `statusline`(자동) 또는 `manual`(사용자 입력)이다.
   - 추정값은 "1% ≈ 단위$"이고, 최근 N개(기본 20) 표본 비율의 **중앙값과 사분위 범위**로 낸다.
   - 표본이 3개 미만이면 %를 보여 주지 않고 단위$만 보여 준다.
4. **상태줄 기록기(선택, M5)**: stdin JSON에서 숫자 필드만 골라 `~/.moni_token/statusline.jsonl`에 덧붙인다(ts, session_id, five_hour/seven_day used_percentage·resets_at, context_window.used_percentage). 같은 값이 연달아 오면 기록하지 않는다.
   - 사용자가 이미 상태줄을 쓰고 있으면 그 명령을 감싸서(래핑) 원래 출력을 그대로 유지한다.
   - 상태줄 설정을 바꾸는 일이므로 **사용자 확인 후** 적용한다.
5. **속도**: 5분 버킷의 단위$/분이다. 도달 예상은 현재 15분 속도로 선형 외삽한다(ccusage와 같은 방식, 근거로 노출).

## 근거

- 토큰 수 그대로는 종류별 비용이 최대 20배까지 다르다(cache_read 0.1× ~ 1h 쓰기 2×). 그래서 "왜 비쌌나"를 설명할 수 없다. 단위$는 원인 유형(캐시 미스와 긴 대화 반복 읽기)을 같은 축에서 비교하게 해 준다.
- 상태줄 값이 있으면 보정은 추정이 아니라 측정이 된다. 없는 환경(API 키 사용자, 상태줄을 원치 않는 사용자)을 위해 수동 보정 경로를 남긴다.
- 실행 중 네트워크로 가격을 받아 오는 방식은 "외부 전송 없음" 원칙과 충돌하므로 배제한다.

## 대안

- claude-monitor식 P90 한도 추정: "한도에 부딪힌 과거 세션"이 필요하고 계획(plan)별 프리셋이 비공식 추정치다. 실측 %가 있으면 쓸 이유가 약하다.
- 토큰 합계를 단위로 쓰는 방식: 단순하지만 위 근거대로 원인 설명력이 없다.

## 결과

- 가격이 바뀌면 `pricing.toml`을 고쳐야 한다. 적용 시작일을 기준으로 과거 호출도 재계산할 수 있다.
- 상태줄 기록기가 없으면 처음 며칠은 % 표시가 비어 있다(의도한 동작).
