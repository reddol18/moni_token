# ADR-0005 — 과거 실행 기반 진행률 예측

- 상태: 승인 (2026-11-05, 사용자 지시 "남은 이슈 진행"으로 구현 담당이 결정)
- 관련: https://github.com/reddol18/moni_token/issues/7 , ADR-0004, CLAUDE.md 절대 규칙 1·2

## 맥락

지도는 에이전트가 지금 무엇을 하는지는 보여 주지만, 얼마나 남았는지는 보여 주지 않는다. 로그에는 몇 달치 서브에이전트
실행이 있다. LLM 없이(규칙 2) 과거 분포만으로 범위를 낼 수 있다.

## 결정

1. **방법: 경험적 분위수, 조건부.** 실행 중인 에이전트가 지금까지 `c`회 호출했으면, 과거 같은 묶음의 완료된 실행 중
   **호출이 `c`회 이상이었던 것만** 골라 전체 호출 수·소요 시간·사용량의 P50/P85를 낸다. 이미 그만큼 온 실행만 비교하므로
   오래 도는 작업이 "곧 끝남"으로 보이지 않는다. 모델 적합·외삽은 하지 않는다.
2. **묶음: `agentType` 우선, 같은 프로젝트에 표본이 충분하면 프로젝트 안에서.** 최근 200개까지. 모델은 묶음에 넣지 않는다
   (표본이 너무 쪼개진다).
3. **표본 하한 10개.** 조건을 건 뒤 10개 미만이면 숫자 대신 "기록 부족 (n=7)"을 보인다. 모든 숫자는 "추정"과 표본 수를 함께 보인다.
4. **남은 사용량.** 실행 중인 에이전트마다 (P50/P85 전체 사용량 − 지금까지) 합을 5시간 보정으로 %p로 바꾼다. 현재 5시간 % +
   P85가 100%를 넘으면 경고한다.
5. **기능(체크리스트) 진행 예측: `check`가 남기는 스냅숏.** 계약 문서마다 (경로, 완료 수, 전체 수, 시각)을 **값이 바뀔 때만**
   기록한다. 완료 사이 간격의 중앙값·85% 값 × 남은 항목 수로 P50/P85 완료 시점을 낸다. 완료가 3번 미만이면 "기록 부족".
   git 이력은 읽지 않는다(외부 프로세스·저장소 구조에 의존하지 않기 위해).
6. **새로 저장하는 것 (규칙 1 범위 안, 숫자·메타데이터만):**
   - `agent_meta`: 서브에이전트 id, 세션 id, 프로젝트 폴더, `agentType`, 완료 여부, 메타 파일 수정 시각. 작업 설명은 저장하지 않는다.
   - `checklist_snaps`: 문서의 프로젝트 기준 상대 경로, 완료 수, 전체 수, 시각. 항목 문장은 저장하지 않는다.
   - 둘 다 `CREATE TABLE IF NOT EXISTS`로 추가해 스키마 버전을 올리지 않는다(DB 재생성 없음).
7. **검증: 백테스트.** 완료된 과거 실행마다, 그 실행보다 **앞선** 실행만으로 고정 시점(호출 1·2·4·8·…회째)의 예측을 만들어
   실제 전체 호출 수가 P50·P85 안에 든 비율을 잰다. `moni-token forecast`로 누구나 다시 잴 수 있다.
   - 처음에는 "각 실행의 호출 절반 시점"으로 쟀는데, 그 시점은 정답(전체 = 지금의 2배)을 아는 셈이라 P50 적중이 88%로
     부풀었다. 실시간과 같은 고정 시점으로 바꿨다.
   - 결과(2026-11-05, 이 PC): 예측 930건, **P85 안 92.4%, P50 안 59.4%**(목표 약 85%, 50%). 범위가 약간 넓다(보수적).
     `general-purpose`는 짧은 일과 긴 일이 섞여 특히 넓다.

## 대안

- 현재 속도로 선형 외삽: 작업 길이의 꼬리가 길어 크게 빗나간다. 기각.
- git 이력으로 체크리스트 과거를 즉시 복원: 빠르지만 외부 프로세스 실행과 커밋 습관에 의존한다. 보류(필요하면 선택 기능으로).
- 모델별 묶음: 표본 부족. 기각.

## 결과

- 처음 쓰는 PC나 새 `agentType`은 한동안 "기록 부족"이 보인다.
- 체크리스트 예측은 스냅숏이 쌓일 때까지(완료 3번) 숫자가 없다.
