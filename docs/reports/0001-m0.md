## 3. ⚠ M3 수용 테스트 전제와 로그가 다름

`E--claude-dev-base-fund-agent` 세션 bec0d341의 로그 실측:

- **15:06~15:56 KST(06:06~06:56Z)에는 호출이 0회다.** 이 시각 무렵 다른 로컬 프로젝트 활동도 없다.
- **15:56:11 KST**: 3시간 공백 뒤 첫 호출에서 `ephemeral_1h` 캐시 쓰기 **458,116토큰**이 발생했다(캐시 만료 → 전체 재기록). 이어서 9회 호출, 호출당 cache_read 약 487k~493k.
- "긴 대화 × 잦은 호출" 패턴은 **12:31~12:56 KST**에 있다. 25분간 약 48회 호출했고, 호출당 컨텍스트는 405k에서 482k로 늘었다.
- 18:47 KST에도 같은 캐시 미스(470,838토큰)가 있었다.
- 정가 환산으로 보면 15:56 재기록 1회(입력가의 2×)가 그 뒤 9회 읽기(0.1×)를 합한 것보다 비싸다. 따라서 그 5%의 주원인은 **"캐시 미스(긴 대화의 재캐싱)"**일 가능성이 크다.

- (a) 12:31~12:56 KST → "긴 대화 × 잦은 호출"(호출 수, 호출당 컨텍스트)

## 4. ADR
- `docs/adr/0001-architecture.md` — stdlib 증분 수집기, message.id 전역 중복 제거(output max), 서브에이전트·워크플로 포함, 본문 미저장 컬럼, LLM/네트워크 금지 테스트(AST 검사 + 소켓 차단).
- `docs/adr/0002-usage-unit-and-calibration.md` — 단위 = 정가 환산 USD(1h 캐시 쓰기 2×, 가격표는 동봉하고 실행 중 받아 오지 않음). 5시간 경계 우선순위: 상태줄 resets_at → quotaLimits → 수동 → 정시 내림 휴리스틱. 보정은 상태줄 자동 기록 + 수동 입력, 비율의 중앙값을 씀.

## 5. PLAN §6 추천안
1. **급증 기준**: 15분 단위$ 속도 ≥ max(직전 60분 5분버킷 중앙값 × 3, 절대 하한) 이면 사건으로 본다.
   - 절대 하한은 M2에서 지난 7일 활성 15분 구간의 p75로 정해 설정 파일에 적는다. 중앙값은 쉬는 시간이면 0이 되므로 하한이 꼭 필요하다.
   - **즉시 사건 1개 추가**: 한 호출의 캐시 쓰기 ≥ 200k토큰(이번 사례를 놓치지 않으려는 것).
   - 상태줄 %가 있으면 15분에 +3%p 이상 오를 때도 사건으로 본다.
   - 재알림은 같은 프로젝트에 30분 간격. 다만 배수가 2배 이상 더 오르면 즉시 알린다.
2. **웹**: **정적 HTML 추천.** 수집 주기마다 `~/.moni_token/report.html`을 다시 생성하고 데이터는 JSON으로 내장한다. 그래프와 드릴다운은 내장 JS로 처리하고 외부 CDN은 쓰지 않는다. 상주 서버·포트가 없어 공격면과 부담이 0이다. localhost 서버는 웹 입력칸이 꼭 필요해질 때만 쓴다.
3. **보정 입력**: **상태줄 자동 기록(주) + CLI 한 줄(보조)**. 예: `moni-token calibrate --from 15:06 --to 15:56 --pct 5`. 웹 입력칸은 서버가 필요하므로 뺀다. 상태줄 설정 변경은 사용자 확인 사항이다.
4. (참고) 상주: 작업 스케줄러로 2분마다 짧게 실행하는 방식을 추천한다(상주 메모리 0). 확정은 M5에서 사용자 확인 후.

## 6. 이 작업이 쓴 토큰(M0 세션 로그를 스크립트로 집계, 보고 직전 시점)
